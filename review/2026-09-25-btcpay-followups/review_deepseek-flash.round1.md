**1. Hook ordering re-opens #11 through the Cancel path (highest).** `afterLaunchDialog` (js/freewallet-desktop.js:327) clears the flag, then runs `checkBtcpayAuth()`. On the Cancel branch of the launch dialog the wallet is locked and `ss.btcpayWallet` is null, so `checkBtcpayAuth` takes its `else` at line 1151 and opens `dialogEnableBtcpay()`. Control then returns to the hook, which runs `checkBtcpayTransactions()` — a new call site — while that dialog is up. `processBtcpayQueue`'s only stacking guard is `$('#btcpay-form').length` (line 1338), the id `dialogBTCpay` builds; if `dialogEnableBtcpay` uses a different id, the guard misses and `dialogBTCpay(false)` → `dialogCheckLocked('make a payment')` stacks a "Wallet Locked!" notice on the enable dialog. That is the exact failure #11 was opened for, just moved from the init tick to the Cancel callback. The same second call also runs when `checkBtcpayAuth` silently stashes (unlock path) — harmless there.

**2. The flag can stick true.** Clearing depends entirely on the launch dialog calling its callback on every terminal path. `dialogPassword` covers both (Cancel → `onCancel`, line 4383; success → `callback()` at 4449), but its OK handler returns without either callback when `err` is set (line 4445) and the dialog is not re-openable-independent — inside `initWallet` that is fine, the dialog stays up. `dialogMigrate(afterLaunchDialog)` passes the hook only as a success callback (line 341). If migration fails or is declined without invoking it, `FW.LAUNCH_DIALOG_OPEN` stays true for the process lifetime with no dialog left to clear it: `processBtcpayQueue` returns at line 1343 forever, so a matched order needing manual payment is never offered — silent loss of the match, no user-visible error. Also, a later lock-icon or `processURIData` unlock never clears the flag, so a stuck flag is unrecoverable without a reload. needs `dialogMigrate`'s terminal paths read to confirm.

**3. `checkBtcpayTransactions()` at hook time runs before network info exists.** `initWallet` fires `checkUpdateWallet()` (line 347) but its API response is async; the hook can run first. `autoBtcpay` dereferences `FW.NETWORK_INFO.fee_info.optimal` unguarded at line 1357. If the queue is populated from cache at that moment, `processBtcpayQueue` → `autoBtcpay` throws before signing: denial (the 60 s tick retries), not a bad tx — but it throws inside a BootstrapDialog button handler, after `checkBtcpayAuth` already stashed. Order in the hook is otherwise correct (auth stash first).

**4. Gates changed, reader not.** `getWallet()` (line 688) is untouched and still returns the hot-swapped seed; every caller of it — `getWalletPassphrase`, `getPrivateKey`, the `cpBtcpay` signing path — still treats a locked swap as an authenticated session. Whether that matters reduces to whether each caller is preceded by `dialogCheckLocked`/`dialogViewPrivateKey`. The diff shows the gates, not the call sites; any menu action or URI handler that calls `getWalletPassphrase()`/`getPrivateKey()` directly still exposes plaintext seed material during the swap window. Unverified in this session.

**5. `checkAutoLock`.** Requiring `isWalletUnlocked()` removes a genuine hazard rather than a relied-on behaviour: the old test fired mid-swap and `lockWallet()` deleted `ss.wallet` under an in-flight `cpBtcpay`. Residual: when the user unlocks *during* a swap, `WALLET_ENCKEY` is set, so `isWalletUnlocked()` is true and auto-lock can still delete the seed under the signing call — #9's skip only protects cleanup, not a concurrent lock. The reverse state (seed present, no key, genuinely unlocked) is reachable only in the harness.

**6. Tests.** The gate is real: `execFileSync` throws on non-zero exit, so a failing tools script fails `npm test`, and the `> 0` check rejects a no-op run. Two gaps: `execFileSync` is given no `timeout`, so node:test's 15-minute limit cannot kill a hung child (three scripts serial); and `autoBtcpay`, `checkBtcpayTransactions`, `dialogMigrate` and `dialogPassword` are all stubs in the new cases, which is why the hot-swap and its `c && !FW.WALLET_ENCKEY` cleanup (line 1390), the migrate failure path, and the pre-`fee_info` call are exactly what the suite does not exercise.
