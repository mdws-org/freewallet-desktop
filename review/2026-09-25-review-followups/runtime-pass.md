# Runtime pass (2026-09-25, commit ed44c96)

Bundle: the app staged by `node build.js` (repo `build/`, production dependencies only), packaged twice from that one staging directory: the shipped `normal`-flavor arm64 bundle (`builds/osx-arm64/FreeWallet.app`, NW.js 0.92.0), and an SDK-flavor bundle of the same files under `/tmp`, because only the SDK flavor keeps DevTools and so honours `--remote-debugging-port`. The SDK bundle was driven over the Chrome DevTools Protocol (a 60-line stdlib Node client; `Runtime.evaluate` against the app page, `Page.captureScreenshot` for the dialogs), with `--user-data-dir` pointing at a throwaway profile so no wallet data on the machine was touched. Every dialog was operated through its own inputs and buttons, not by calling the functions behind them. Waits after each password action are for PBKDF2 (310k iterations).

| Step | Observed |
|---|---|
| Launch, no wallet | Welcome dialog. Create New Wallet, passphrase acknowledged, "Set a wallet password" dialog. |
| New-password rules | `short 1`: "Wallet password must be at least 12 characters long". `no digits here at all`: "must contain at least 1 number". Mismatched confirmation: "Password and Confirmation password do not match!". `runtime pass pw 1` twice: wallet created, `walletVault` on disk, `walletEncrypted` 1, no legacy keys, unlocked, address shown. |
| Lock icon | Click: `ss.wallet` gone, derived key gone, icon shows locked. Click again: "Enter wallet password". Wrong password: "Invalid password", dialog stays, still locked. Right password: "Wallet unlocked", key in memory, icon shows unlocked. |
| Change password (Settings, Wallet tab) | Button "Change Wallet Password" present. Dialog "Change wallet password" with Current / New / Confirm New fields. Wrong current: "Current password is not correct". Weak new: "at least 12 characters". `runtime pass pw 1` to `changed pass pw 2`: "Wallet password changed". After a reload: old password "Invalid password"; new one unlocks. |
| Auto-BTCpay, Cancel path | One order with `autopay: 1` recorded in `btcpayOrders`. Reload: unlock dialog. Cancel: `skipWalletAuth` set, then "Enable Auto-BTCpay?" opens on its own (not on top of the unlock dialog) with the disclosure paragraph; screenshot `s2-enable-btcpay.png`. Enable with the password: `btcpayWallet` and `btcpayKeys` in sessionStorage, wallet re-locked, no key in memory, "Auto-BTCpay Enabled". |
| Stash across lock | Unlock: stash still present beside `ss.wallet`. Lock from the icon: `ss.wallet` and key gone, both stash entries remain. |
| Stash across app restart | Quit and relaunch: sessionStorage empty; unlock dialog. So "closing the app" in the disclosure is true. |
| Disable | Cancel the unlock, "Enable Auto-BTCpay?", Disable, confirm "Yes": `btcpayOrders` flag 0 on disk and in `FW.BTCPAY_ORDERS`, no stash, dialog closed. |
| Order form (shipped file) | `html/exchange/order.html` in the bundle carries the consent text ("... a copy of my wallet seed and imported keys stays in the app's session memory, also while the wallet is locked, until I disable Auto-BTCPay, log out, or close the app") and stashes only when `autopay==1`. Not exercised end to end (needs a broadcast order). |
| Legacy migration on a 7-character password | The live seed re-encrypted as v1 blobs under `seven77` (`wallet`, `walletKeys`, `walletPassword` = AES(pw, pw), `walletEncrypted` 1), vault removed, reload: "Upgrade wallet security". `wrong77`: "Invalid password". `seven77`: "Wallet ready" with the kept-password paragraph ("... does not meet the requirements now applied to a new wallet password ... You can change it under Settings, on the Wallet tab."); vault written, legacy blobs retained, unlocked. |
| Damaged vault, backup present | Vault's `wallet` blob overwritten at its tail, reload: unlock dialog (not the welcome screen). `wrong77`: "Invalid password", record still damaged. `seven77`: "The stored wallet was damaged and has been rebuilt from the copy kept from before the encryption upgrade. Your wallet is now unlocked and available for use."; vault repaired, unlocked, legacy blobs still present. |
| First normal unlock after the rebuild | Reload, `seven77`: "Wallet unlocked"; legacy blobs discarded; the address is the one the wallet was created with. |

Screenshots taken during the pass (`s0-launch`, `s1-settings`, `s2-enable-btcpay`, `s3-migrated`, `s4-rebuilt`) are not committed; the dialog text above is what they showed.

Not covered live: a real matched order paying while locked (needs a funded order on the DEX), and the manual-payment notice that upstream stacks on the launch dialog when a queued match exists (unchanged by this patch).
