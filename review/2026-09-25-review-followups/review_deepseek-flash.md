## Ranked findings

**1. The stash is re-created silently at every unlock; the disclosure is shown only once, at opt-in.** `checkBtcpayAuth` (1073-1095) writes `btcpayWallet`+`btcpayKeys` with no dialog whenever any order carries `autopay==1`, `btcpayWallet` is null and `wallet` is not (1087-1091). Those flags persist in `ls btcpayOrders` (cleared only by `resetWallet`, 364). Post-patch that call runs as `dialogPassword`'s success callback (322) — i.e. precisely while `ss.wallet` is set — so on every launch after the original opt-in the seed and imported WIFs return to sessionStorage the moment the password is typed, and the paragraph added at 4892 is never seen again. Pre-patch the same call ran while locked, so `wallet` was null and it reached `dialogEnableBtcpay()`; the silent branch is a behaviour change introduced by the fix-3 routing, not just a doc gap. State: vault on disk, `btcpayOrders` with one `autopay:1`, session empty, launch, unlock. Compounding: the "Disable" confirm (4902-4907) only closes the dialog — nothing in that branch clears the per-order autopay flags or the stash, so a user who reads the new paragraph and disables still has auto-pay on next launch.

**2. sessionStorage survives a page reload, so the stash outlives its stated lifecycle and can sign before any password entry.** Both the dialog text (4892) and the `lockWallet` comment (664-670) say the copy lives "until you log out or close the app". A window reload keeps sessionStorage; `FW.WALLET_ENCKEY` is memory-only and gone. `initWallet` clears `ss.wallet` (311) but nothing clears `btcpayWallet`/`btcpayKeys` — only `resetWallet` (367-368) does. `processBtcpayQueue` (1248-1254) treats `(a||b)` as "can auto-pay" and `autoBtcpay` (1283-1297) hot-swaps the stashed seed back into `ss.wallet`. So after a reload the first queue tick can sign and broadcast a matched order in a session where no password has been entered, and `checkAutoLock` cannot intervene (no `ss.wallet`). This is the same capability a person at the machine gets.

**3. Fix 5's outcome is wrong for the state that has a legacy backup (Q5).** `decryptWallet` (539-556) calls `discardV1Backup()` only on success, and `migrateWalletToV2` (613-617) intentionally leaves `wallet`/`walletKeys`/`walletPassword` in place until the first successful v2 unlock. So with a damaged v2 `wallet` blob, an intact `crypto` descriptor, and the v1 blobs still on disk: `initWallet` (305-326) takes the `hasV2` branch, `dialogMigrate` is unreachable, and the new message (4327) sends the user to the 12-word passphrase. The local v1 blobs are decryptable by the same password and are what `migrateWalletToV2` would rebuild the vault from. Telling the user to re-derive from the passphrase is the riskier instruction here (wrong or non-BIP39 phrase yields a different address set, and the rebuild writes over the damaged record). That state should attempt the v1-backed rebuild, or at minimum the error should name the backup.

**4. `readVault()` conflates "absent" with "unparseable".** It returns null in the catch (505-511), so a `walletVault` record whose JSON is truncated — after an earlier successful unlock has discarded the v1 blobs — gives `hasV2=false, hasV1=false`, and `initWallet` opens `dialogWelcome()`, the create-a-new-wallet flow. The lock icon's new `else if(readVault())` is inert in the same state (Q3). Repair-in-place is possible at that moment and destroyed by the first `writeVault` (523), which overwrites the record. The other Q3 states are fine: v2-with-v1-backups behaves as v2; mid-migration is correct because `writeVault` has already landed; a v1-only locked wallet has an inert icon but is moot, since the migrate dialog is non-closable — which is itself the dead end: a legacy wallet whose blobs fail to decrypt can only produce "Invalid password" with no Cancel and no second route.

**5. `btcpayKeys` is a snapshot with no refresh point.** It is written only at 1089-1091 / 4926-4927. A key imported later never reaches the stash, so `autoBtcpay` (1291-1294) restores a stale set, signing fails for that imported address, and the order is left queued. Conversely a key that leaves `FW.WALLET_KEYS` stays in sessionStorage in cleartext for the window's life. The added test asserts only that the two stash keys move together, not that either tracks the wallet.

## The other questions

**Q2.** The old code fired `callback()` at the end of the non-`err` branch, and an invalid password did not set `err` — so a wrong password *also* invoked the callback. Callers now lose it on a wrong password and on Cancel (4292-4298 never calls it). I could not open `processURIData`; the thing to check is whether its callback clears the pending-action state. If it does, a wrong password or Cancel leaves the URI action armed and it re-fires on the next successful unlock. For `checkBtcpayAuth` the routing orders correctly relative to the modal (it now runs with the wallet open), but that ordering is what produces finding 1.

**Q4.** `dialogCheckLocked` (4508-4513) plus the passphrase being readable from the same tab already concedes everything a current-password prompt would protect: the seed is in memory and the recovery phrase is on screen. Requiring the old password would add ceremony against lockout-by-attendant, nothing against theft.

**Q6.** The harness runs only the extracted storage functions and explicitly does not run the dialogs, so everything this patch actually changed — guard order in the two dialogs, the `decryptWallet`-false branches, callback placement, `dialogCheckLocked` gating, `readVault` parse failure, the index.html and settings.html wiring — is unexercised; all 25 pass with any of them broken. `checkBtcpayAuth`, `processBtcpayQueue` and `autoBtcpay` are not extracted at all; a case setting `FW.BTCPAY_ORDERS` with `autopay:1` against an unlocked mock session would have caught 1, and one leaving `ss.btcpayWallet` set with the key cleared would have caught 2.
